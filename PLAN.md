# Мини-CRM «Объекты и задачи»: реализация и распределение между агентами

Дата плана: 4 ноября 2026 года.

## 1. Цель и обязательные условия

Создать опубликованную CRM по [техническому заданию](https://docs.google.com/document/d/1dpyRJ1E__eD0cisYSj0GDml4xtTTPaLe/edit), подготовить репозиторий, объяснение для руководителя и материалы для созвона.

**ТЗ имеет приоритет над дополнительными идеями.** MVP включает все обязательные функции, а не только демонстрационный интерфейс.

Порядок приоритетов:

1. Правильная логика и защита данных в базе.
2. Все обязательные пользовательские сценарии.
3. Работа опубликованного приложения.
4. Понимание реализации пользователем.
5. Визуальная полировка.

**Текущая точка на момент составления плана:**

- Supabase подключён; проект `jrhmiywbbpnwphubtlcw` активен.
- Прикладных таблиц и миграций пока нет.
- Открытая регистрация отключена и проверена через Auth API.
- URL и публичный ключ проекта получены.
- GitHub подключён, аккаунт `Posseydonn`.
- Аккаунт Vercel существует; доступ для публикации ещё предстоит подтвердить.
- Исходная рабочая папка: `A:\тестовое`, до сохранения плана пустая.
- Бюджет дальнейшей работы — ориентировочно 5–6 часов, включая проверки и подготовку.

## 2. Стек и интерфейс

**Фиксируем стек:**

- React + TypeScript + Vite.
- React Router.
- Supabase Auth, PostgreSQL, RLS и SQL-функции.
- `supabase-js`.
- **Ant Design (`antd`) — единственная основная UI-библиотека.**
- CSS для компоновки и адаптации.
- GitHub и Vercel.

Отдельный Node.js-сервер, Redux, вторую UI-библиотеку и готовый административный шаблон не добавляем.

### Компоненты Ant Design

| Часть приложения | Компоненты |
|---|---|
| Каркас и навигация | `Layout`, `Menu`, `Typography` |
| Вход и формы | `Form`, `Input`, `Select`, `Button` |
| Списки объектов и задач | `Table` |
| Данные задачи | `Descriptions`, `Tag` |
| История | `Timeline` |
| Комментарий при возврате | `Modal`, `Input.TextArea` |
| Подтверждение удаления | `Popconfirm` |
| Ошибки, ожидание и пустые списки | `Alert`, `Spin`, `Empty` |

Оформление: светлая тема, синий акцент, русская локализация. Статусы обозначаются текстом и цветом. На узком экране навигация сворачивается, таблицы при необходимости прокручиваются внутри контейнера.

Дизайн не должен задерживать реализацию обязательных требований.

### Обязательные экраны

1. Вход по email и паролю.
2. Список объектов.
3. Объект со списком доступных задач.
4. Задача: поля, разрешённые действия, история.
5. «Мои задачи» исполнителя.

Постановщик получает формы создания, редактирования и удаления. Исполнитель получает только доступные действия со статусом.

## 3. Данные, права и бизнес-правила

### Структура базы

- **Профили:** идентификатор Auth, имя, роль.
- **Объекты:** название, адрес, время создания, отметка удаления.
- **Задачи:** название, описание, объект, исполнитель, статус, автор, дата создания, отметка удаления.
- **История:** задача, предыдущий и новый статусы, пользователь, время, комментарий.

В базе задаём обязательные поля, внешние ключи, допустимые роли и статусы, индексы связей. Названия и адрес не могут состоять из пробелов; описание допускается пустым.

Автор и дата создания определяются базой. Назначать задачу можно только исполнителю.

### Чтение и роли

- Постановщик видит все активные объекты и задачи, включая созданные другими постановщиками.
- Исполнитель видит только свои активные задачи.
- Объект доступен исполнителю при наличии в нём его активной задачи.
- В общем объекте чужие задачи не раскрываются.
- История доступна вместе с задачей.
- Полный список исполнителей доступен постановщику.
- Для отображения автора и истории исполнителю доступны только необходимые безопасные поля связанных профилей.
- Роль назначается административно; пользователь не может повысить её самостоятельно.
- Неавторизованный пользователь не получает рабочие данные.

Все прикладные таблицы защищены RLS. Проверка роли не должна создавать рекурсивные политики.

### Изменение данных

Изменения выполняются через SQL-функции RPC:

- Создание, редактирование, мягкое удаление объекта.
- Создание, редактирование, мягкое удаление задачи.
- `change_task_status(task_id, target_status, comment)`.

Прямая клиентская запись в таблицы запрещена. Функции самостоятельно проверяют пользователя, роль и допустимость действия. У функций с повышенными правами фиксируется `search_path`, ограничиваются разрешения вызова.

Редактирование задачи не позволяет произвольно изменить статус, автора или дату создания.

### Переходы статусов

| Из | В | Кто |
|---|---|---|
| Создание | Новая | Постановщик |
| Новая | В работе | Назначенный исполнитель |
| В работе | На проверке | Назначенный исполнитель |
| На проверке | Принята | Постановщик |
| На проверке | На доработке | Постановщик, комментарий обязателен |
| На доработке | В работе | Назначенный исполнитель |

Другие переходы запрещены базой.

Изменение статуса и запись истории выполняются одной транзакцией. Перед изменением блокируется запись и проверяется её актуальное состояние. Одновременные или повторные запросы не должны создавать недопустимый переход или двойную историю.

### Допущения, включаемые в сдачу

- Удаление мягкое, история сохраняется; отдельного экрана архива нет.
- Удаление объекта скрывает и его задачи.
- Удалённые записи изменять нельзя.
- Переназначение сохраняет статус: старый исполнитель теряет доступ, новый видит полную историю.
- Редактирование полей не меняет статус, в том числе у принятой задачи. Повторного открытия нет.
- Создание фиксируется в истории как переход в «Новая».
- Историю изменений названия и описания не добавляем.
- Постановщики имеют одинаковые права.
- После действия перечитываем данные. Realtime не добавляем.
- Для чужой записи показываем «Недоступна или не найдена».

## 4. Распределение работы по чатам и агентам

Используем исходный чат как координационный. Отдельные чаты пользователь создаёт для конкретных направлений.

Каждый агент получает этот план, исходное ТЗ, свою область ответственности и требование не изменять чужие участки без согласования с координатором.

### Агент 1 — основа и интеграция

**Ответственность:**

- Инициализация проекта и Git.
- Установка зависимостей, включая Ant Design.
- Общий каркас, тема, русская локализация, маршрутизация.
- Клиент Supabase, состояние авторизации.
- Общие типы запросов и обработка ошибок.
- Сборка, подключение GitHub и ранняя публикация Vercel.
- Финальная интеграция работы остальных агентов.

**Исключительное владение:** зависимости, lock-файл, настройки сборки, общие конфигурации, основной роутер и общие контракты.

### Агент 2 — база и безопасность

**Ответственность:**

- SQL-миграции, ограничения, RLS.
- RPC для объектов и задач.
- Статусы, история, блокировки и мягкое удаление.
- Типы базы и документация интерфейса RPC.
- Применение миграций к Supabase и проверка рекомендаций безопасности.

**Исключительное владение:** миграции и изменения облачной схемы. Другие агенты самостоятельно Supabase не меняют.

**Первый результат:** контракт данных и RPC для остальных агентов — названия, аргументы, возвращаемые данные, статусы и ошибки. Агент 2 определяет контракт базы; агент 1 интегрирует его в общий слой фронтенда.

### Агент 3 — экраны CRM

**Ответственность:**

- Объекты, карточка объекта.
- Карточка задачи, история, «Мои задачи».
- Формы создания, редактирования и действий.
- Загрузка, ошибки, пустые состояния, адаптация.

Работает на Ant Design и согласованном контракте. До готовности базы допустимы временные вымышленные данные внутри разработки; в сдаваемой версии все рабочие действия подключаются к Supabase.

Не меняет миграции, зависимости и общий роутер — передаёт необходимые изменения интегратору.

### Агент 4 — проверки и сдача

**Ответственность:**

- Матрица требований и сценариев проверки.
- Скрипт прямых API-проверок с обычными пользовательскими сессиями.
- Проверка опубликованной версии.
- README, допущения, объяснение руководителю.
- Сценарий демонстрации и вопросы для подготовки.

Начинает с проверочных сценариев параллельно разработке. Фактические результаты записывает только после выполнения.

### Правила совместной работы

- До параллельного редактирования основы агент 1 создаёт проект и фиксирует общие зависимости.
- Агент 2 согласует контракт до подключения экранов к базе.
- Общие настройки меняет только интегратор.
- При работе в одной папке агенты редактируют только свои участки; интегратор выполняет общие Git-операции.
- При использовании отдельных worktree результаты передаются коммитами, интегратор объединяет их.
- Каждый отчёт содержит: что изменено, что проверено, что осталось и нужны ли изменения контракта.
- Пароли, токены и секретные ключи не копируются между чатами. Используются локальные переменные окружения.
- Параллельная работа не заменяет финальную общую проверку.

## 5. Этапы от текущей точки до MVP

### Этап A. Основа и контракт — первые 30–45 минут

Агент 1 создаёт основу, устанавливает Ant Design, настраивает вход и раннюю публикацию. Агент 2 параллельно проектирует схему и выдаёт контракт. Агент 4 составляет матрицу проверок.

**Контрольная точка:** проект собирается, оболочка опубликована, согласован интерфейс базы и фронтенда.

### Этап B. База и интерфейс — следующие 75–90 минут

Агент 2 реализует и применяет миграции. Агент 3 собирает экраны. Агент 1 завершает авторизацию и общий слой запросов.

Создаём через Supabase Auth двух постановщиков и двух исполнителей. Если административного инструмента создания пользователей нет, используем Dashboard; прямые вставки во внутренние таблицы Auth запрещены.

Готовим три объекта и задачи разных статусов, включая общий объект с задачами двух исполнителей. Данные вымышленные; история формируется через штатные операции.

**Контрольная точка:** база проверяет права, пользователи входят, демонстрационные данные готовы.

### Этап C. Интеграция — следующие 45–60 минут

Подключаем экраны к реальным данным. Удаляем временные заглушки из рабочих сценариев.

Проверяем полный цикл: создание → работа → проверка → доработка → повторная проверка → принятие.

**Контрольная точка:** все обязательные действия выполняются через интерфейс.

### Этап D. Безопасность и исправления — 45–60 минут

Проверки выполняются под реальными пользовательскими сессиями:

- Все разрешённые и запрещённые переходы.
- Возврат без комментария и с пробелами.
- Доступ к чужой задаче, истории и объекту по идентификатору.
- Чужие задачи внутри общего объекта.
- Попытки изменить поля, назначение и роль исполнителем.
- Прямые изменения таблиц и подделка истории.
- Доступ без авторизации и регистрация через API.
- Одновременные изменения статуса.
- Потеря доступа после переназначения.
- Удаление объекта и запрет изменения удалённых задач.
- Очистка данных при смене аккаунта.

**Контрольная точка:** обязательные проверки проходят; результаты зафиксированы.

### Этап E. Финальная публикация и сдача — 25–35 минут

- Проверка TypeScript и production-сборки.
- Проверка отсутствия секретов.
- Финальная публикация на Vercel.
- Проверка входа, прямых ссылок и обновления страниц.
- README, миграции, инструкция проверки.
- Текст для руководителя и список допущений.
- Сообщение для hh.ru со ссылками и отдельными тестовыми доступами. Отправляет пользователь.

### Этап F. Подготовка к созвону — 45–60 минут

Разбираем вход, роль, правило доступа, функцию смены статуса, историю и один API-тест.

Пользователь должен уметь объяснить:

- Где работает интерфейс, а где проверяются права.
- Почему скрытой кнопки недостаточно.
- Почему публичный ключ допустим во фронтенде.
- Как статус и история сохраняются вместе.
- Почему исполнитель не получает чужие задачи.
- Какие решения приняты самостоятельно.

Проводим демонстрацию полного цикла под разными аккаунтами. Использование ИИ не скрываем: ТЗ его разрешает, но требует понимания результата.

## 6. Критерии готовности

MVP готов, когда:

- Все требования ТЗ реализованы на опубликованном сайте.
- Права и переходы проверяются базой.
- История защищена от самостоятельной записи через API.
- Есть тестовые пользователи и данные.
- Есть GitHub с миграциями и README.
- Проверки выполнены, ограничения описаны.
- Подготовлены четыре составляющие сдачи: сайт с доступами, репозиторий, объяснение руководителю, решения и допущения.
- Пользователь способен объяснить ключевой сценарий по коду.

Если не укладываемся во время, сокращаем оформление и дополнительные удобства. Обязательные функции и проверки безопасности не исключаем. Непройденный обязательный пункт означает, что работа ещё не завершена.
