## Замечания

### R1 — P2: списки и история могут обрезаться без предупреждения

Место: `src/pages/crm/shared.tsx:24–32`, `src/lib/api.ts:17–22`.

Запросы списков не используют range и не контролируют полноту результата. Табличная пагинация (`shared.tsx:82`) делит только уже полученный массив. При превышении настроенного Max Rows API пользователь перестанет видеть старые задачи/объекты и поздние записи истории. В демо с шестью задачами проблема не проявляется; точный текущий лимит облака не проверялся.

Исправление: серверная пагинация списков с count и стабильной сортировкой по времени и id; историю загружать страницами. Поиск и фильтры применять в запросе. Проверить на объёме выше лимита API.

Документация: https://supabase.com/docs/reference/javascript/v1/select (стандартный лимит 1000), https://supabase.com/docs/reference/javascript/using-modifiers-range .

### R2 — P2, дополнительное усиление безопасности: сайт допускает встраивание

Место: `vercel.json:1–13`.

Свежий HEAD-запрос опубликованного приложения не вернул CSP/frame-ancestors или X-Frame-Options. HSTS присутствует. Это оставляет возможность clickjacking: чужая страница может обманом направлять клики авторизованного пользователя на доступные ему операции CRM. Это не обход RLS и не доказательство состоявшейся атаки.

Исправление: запретить встраивание через Content-Security-Policy frame-ancestors 'none' и X-Frame-Options DENY; проверить заголовки после публикации. Полную CSP вводить отдельно с проверкой совместимости Ant Design.

### R3 — P3: чтение данных продублировано в UI

Место: `src/pages/crm/shared.tsx:13–34` и `src/lib/api.ts:17–28`.

Адаптер экрана практически повторяет чтения общего API ради AbortSignal. Это понятный след разделения работы агентов, но при дальнейшем изменении фильтров, сортировки или пагинации две реализации могут разойтись. Сейчас расхождения прав из-за этого не обнаружены: доступ ограничивает база.

Исправление: общий слой запросов с необязательным AbortSignal; UI должен содержать состояние загрузки и отображение.

### R4 — P3: инструкция ошибочно называет followup-проверку неизменяющей данные

Место: `supabase/tests/README.md`, раздел «Проверки облачного API»; `supabase/tests/hosted-followup.ps1:13–25`.

Скрипт делает update_object, пробует PATCH/удаление и меняет metadata пользователя. При регрессии защиты отрицательная проверка удаления может реально удалить демонстрационный объект. Повторно не запускался. Утверждение «без создания записей» буквально верно, но недостаточно описывает последствия для существующих данных.

Исправление: явно описать изменения и запускать негативные мутации только на изолированных фикстурах/тестовом проекте. Для действительно read-only проверки выделить другой скрипт.

## Оценка структуры и безопасности

Для небольшого тестового архитектура соразмерна: отдельного лишнего сервера и хранилища состояния нет; типы строгие; автор/время задаются базой; роли не берутся из пользовательских metadata. SECURITY DEFINER-функции фиксируют search_path и явно ограничивают EXECUTE; запись доступна через проверяющие RPC. История записывается в той же транзакции, что статус. Данные выводятся средствами React, опасных HTML-вставок в просмотренных экранах нет. Provisioning обработчик в репозитории возвращает 410 без привилегированных операций; текущая облачная версия в этом ревью не запрашивалась.

Приоритет перед сдачей: устранить R1/R2 либо явно принять ограничения демо, затем свежая hosted/browser приёмка по этапу D и материалы этапов E/F. Большая переделка архитектуры по результатам ревью не требуется.
