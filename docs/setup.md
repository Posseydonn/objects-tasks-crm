# Запуск с новым Supabase

Эта инструкция предназначена для **нового пустого проекта**, а не для существующей демобазы. Пароли и привилегированные ключи в файлы репозитория не записывайте.

1. Установите Node.js 24, выполните `npm ci`.
2. Создайте проект Supabase. В Dashboard → Authentication → Providers → Email отключите **Allow new users to sign up**. Сохраните настройку. Оставьте вход по email/паролю включённым.
3. В SQL Editor нового проекта выполните целиком, строго по очереди:
   - `supabase/migrations/20261104201811_crm_initial.sql`;
   - `supabase/migrations/20261104201920_restrict_internal_rls_trigger.sql`.
   Это способ ручной установки схемы; он не регистрирует версии в истории Supabase CLI. Не смешивайте его с последующим `db push` без согласования migration history. Не запускайте файлы повторно на уже установленной схеме.
4. Через Authentication → Users → Add user создайте минимум одного постановщика и двух исполнителей с email и паролями. Подтвердите email административно (Auto Confirm User). Скопируйте UUID каждого пользователя. Не вставляйте пользователей SQL-запросом в `auth.users`.
5. В SQL Editor создайте соответствующие профили. Замените три UUID реальными идентификаторами из Auth; это не пароли:

```sql
begin;
insert into public.profiles (id, full_name, role) values
  ('00000000-0000-0000-0000-000000000001', 'Постановщик', 'manager'),
  ('00000000-0000-0000-0000-000000000002', 'Исполнитель 1', 'executor'),
  ('00000000-0000-0000-0000-000000000003', 'Исполнитель 2', 'executor');
commit;

select id, full_name, role from public.profiles;
```

Auth и профиль — две разные записи. Вход без профиля не даёт рабочей роли. Если UUID ошибочен, внешний ключ не даст создать профиль; транзакция откатится целиком.

6. Скопируйте `.env.example` в `.env.local`. Укажите URL проекта и **publishable key** из Dashboard → Connect/API Keys. `service_role`, secret key и пароль базы приложению не нужны.
7. Запустите `npm run dev`, войдите постановщиком, создайте 2–3 объекта и задачи для обоих исполнителей. Статусы формируйте обычными действиями пользователей, чтобы история оставалась корректной. Не запускайте hosted-security.mjs для наполнения уже используемой базы.
8. Проверьте вход обоих исполнителей и недоступность чужой задачи по ссылке. Убедитесь, что форма регистрации отсутствует и регистрация отключена именно в настройках Auth.
9. Для публикации задайте обе переменные `VITE_SUPABASE_*` из `.env.example` в Vercel Production. Команды сборки и прямые маршруты уже настроены в `vercel.json`. Выполните `npm run build`, затем публикацию Vercel. Пароли пользователей не добавляются в переменные фронтенда.

Для локальных SQL-тестов: `npm ci --prefix supabase/tests` и `npm test --prefix supabase/tests`. Они не настраивают ваш облачный проект. Для браузерной приёмки см. [browser-verification.md](browser-verification.md).
